# 0008 - eBay as the price oracle, other sources as valuation clients

**Supersedes the Depop half of `0001-multi-source-connector-strategy.md`.**

**Context:** ADR 0001 split sources by *how they can be accessed*: eBay and Depop pull-based on a schedule, Facebook Marketplace push-based through a browser extension. That axis is still correct, but it quietly implied a second thing that turns out to be wrong, namely that every pull-based source feeds sold-price history the same way. ADR 0001 says outright that Depop "gets checked periodically by `disappearance_check.py` ... to build sold-price history", and `CLAUDE.md` and `PROJECT_PLAN.md` repeat it. The actual goal of this project is narrower and clearer than that: build a reliable picture of what specific items are worth **on eBay**, and use that picture to judge items found anywhere. Depop and Facebook Marketplace carry far too much item variety for per-item price history built from them to mean anything: a handful of loosely-described one-off listings does not make a comparable-sales dataset, and averaging across them would produce confident numbers with nothing behind them. Worse, mixing them into the same comp pool as eBay would quietly contaminate the one source that does have the volume and catalog structure to support this.

**Decision:** Separate *how a source is accessed* from *whether its prices are trustworthy enough to price against*, because they are independent properties that ADR 0001 conflated. **eBay is the sole comp source**: it alone is ingested, disappearance-tracked, scored for sale confidence, and used to answer "what is this item worth". **Depop and Facebook Marketplace are valuation clients**: their listings are captured and scored *against* eBay-derived value, and they contribute exactly zero comps. Depop remains pull-based and polled on a schedule, but purely so the system can automatically surface Depop items that look underpriced relative to eBay; it is never disappearance-checked and never produces a `likely_sold` row, so ADR 0001's access-shape decision survives while its history-building implication does not. Facebook stays push-based via the extension, unchanged. In code the distinction becomes explicit before Depop exists, so that adding a client to `PULL_BASED_SOURCES` cannot silently enrol it in comp building: a separate `COMP_SOURCES` frozenset gates disappearance checking, and a test asserts a polled non-comp source is never checked. Finally, because a listing found on another site has no eBay catalog id, matching it to eBay value is an inference, so a cross-source match is surfaced as a **best guess with a confidence score, shown alongside the comps it used**, rather than silently driving a deal score.

**Alternatives considered:** Keeping Depop in disappearance tracking and simply down-weighting its comps was rejected: the problem is not that Depop comps are noisy but that they are mostly meaningless, since "the same item" is far fuzzier there, and a weight cannot rescue a comp set whose members are not actually comparable. It would also spend scarce disappearance-check budget on data the valuation engine should ignore. Dropping Depop entirely and supporting only Facebook was considered, and rejected because polling Depop is cheap now that it contributes no comps, and automatically surfacing underpriced Depop items is genuinely useful in a way that manual capture is not. Deriving comp-eligibility from source at each query site (`WHERE source = 'ebay'` scattered through stage 4) was rejected in favour of one named set, because the rule is a project-level decision that deserves one place to read it and one place to change it. Automatically scoring cross-source matches without showing the user the match was rejected: a wrong identification produces a confidently wrong deal score, and there is nothing in a bare number that prompts anyone to check it.

**Consequences:** The valuation engine's comp query gains a mandatory `source` constraint, and stage 4 must treat `COMP_SOURCES` as a hard filter rather than a preference. Disappearance checking, the sale-confidence scoring in `0005`, and the relist detection it depends on all become eBay-only concerns by definition, which simplifies them: `image_hash` relist matching no longer has to reason about cross-source photo reuse at all. Conversely the **hard problem of the project moves**, from "build comps from several sources" to "identify what an item found elsewhere actually is", which is a genuinely different problem that nothing in the codebase currently addresses. That makes stage 3's feature pipeline load-bearing in a way the original build order did not anticipate: `epid` (eBay's catalog id) answers product identity exactly for eBay-internal comps but is absent on every foreign listing, so image embeddings and text extraction are the only available bridge. `image_hash` also acquires its real purpose, which is not the duplicate-merging ADR 0002 imagined but identification, since a foreign seller reusing a stock photo can be matched instantly and cheaply before any model runs. `SavedSearch` still does not apply to Facebook, as ADR 0001 noted, and now also does not imply comp collection for Depop.
