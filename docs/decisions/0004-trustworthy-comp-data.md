# 0004 - Trustworthy comp data: price history, buying options, shipping, and two-strike sold confirmation

**Context:** Stage 4's valuation engine will treat every `likely_sold` listing as a comparable sale, so the quality of that data sets a hard ceiling on how good a deal score can ever be. An audit of the intake path found four ways it is currently worse than it looks. First, `ingest_saved_search` overwrites `existing.price` on every run, so a price *drop*, one of the strongest deal signals available, is invisible, and the "price-history chart" `PROJECT_PLAN.md` specifies for stage 6 is unbuildable. Like sold history itself, this accrues in wall-clock time: history not captured today cannot be recovered later. Second, eBay's `itemSummary` includes `shippingOptions[].shippingCost` in the payload already being fetched, and the normalizer discards it, even though `PROJECT_PLAN.md` already flags item-price-only comparison as "a real correctness bug once stage 4's valuation engine is scoring how good a deal something is". Capturing it costs nothing extra. Third, and worst, `itemSummary` includes `buyingOptions` and the normalizer discards that too. For an `AUCTION` listing, `price` is the *current bid*, not an asking price: it changes every few hours, and when the auction ends the listing vanishes and gets recorded as sold at whatever mid-auction bid happened to be observed last. That is not a sale price, and there is currently no way to even measure how much of the corpus it affects. `BEST_OFFER` listings have a milder version of the same problem, since they sell below asking. Fourth, a single 404 permanently marks a listing sold, and since `likely_sold` is terminal (the check only ever queries `status = 'active'`), one transient 404 becomes a permanent false comp.

**Decision:** Capture what is already being thrown away, and stop trusting a single observation. Add a `PriceObservation` table, append-only, written on first insert and thereafter only when price or shipping actually changes, so the row count tracks real events rather than ingest frequency. Add `shipping_cost`, `is_auction`, and `accepts_best_offer` to `Listing`, the latter two derived from `buyingOptions` at normalization time as typed indexed booleans rather than a raw JSON list, because stage 4's hot comp query needs to filter on them and `images` already demonstrates that plain `sa.JSON` gets no index. Require **two consecutive** failed lookups before marking a listing `likely_sold`: the first 404 records `missing_since` and leaves the listing active, the second confirms it. This costs one extra call per genuine sale, which is cheap because sales are a small fraction of checks, and it yields better data than it costs, since `missing_since` is a closer estimate of when the item actually left the market than the confirmation timestamp is. Also record each saved search's result `total` on `SavedSearch`, so it becomes a fact which searches are truncated by eBay's 200-result cap rather than a guess.

**Alternatives considered:** Storing price history as a JSON array on `Listing` was rejected: it grows unboundedly inside a row that is read on every ingest, and it cannot be queried or aggregated, which is exactly what a price chart and a trend signal need. Writing a `PriceObservation` on every ingest regardless of change was rejected as well, since at hourly ingest that is roughly 250,000 rows a day that mostly say "nothing happened"; recording only changes keeps the table proportional to real events. Keeping the raw `buyingOptions` list as JSON was rejected for the indexing reason above, and because only two facts out of it actually matter. Excluding auctions at ingest time (never storing them at all) was considered and rejected: an auction's *final* price is genuinely useful comp data once disappearance confirms it ended, and discarding the listing outright would throw that away along with the problem. Marking sold on a single 404 was the existing behavior and is cheaper by one call per sale, but a false positive is permanent and silently corrupts the one dataset this project exists to build, which is a bad trade at any price.

**Consequences:** Sold-detection latency grows by one check cycle, since confirmation now needs a second pass. Combined with the budget from `0003`, a sale is recorded up to two cycles after it happens rather than one, and stage 4 must keep treating `likely_sold` as "left the market at roughly this price" rather than "sold at this price". The new `is_auction` flag finally makes the auction problem measurable, and the first real question to ask of the data once it lands is what fraction of the corpus it covers; if it is large, stage 4 will need to weight or exclude those comps, and this ADR does not decide that. `PriceObservation` is the first table besides `Listing` that grows per-event rather than per-listing, so it is the first candidate for a retention policy, though at roughly 40 bytes a row that is far away. `SavedSearch` gains observability fields that nothing reads yet; they exist to inform the deferred pagination work with real numbers. Finally, the shipping and buying-option field shapes are taken from eBay's documented `itemSummary` schema but have not been seen in a live response from this application, because the daily quota was exhausted when this was written: the fixture encodes the expected shape and must be checked against a real response before these fields are trusted.
