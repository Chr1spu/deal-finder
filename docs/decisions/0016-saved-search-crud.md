# 0016 - Saved-search CRUD, and refusing to let it exhaust the quota

**Context:** Saved searches are the only lever on what this system sees. Everything downstream (embeddings, comps, valuation, the deal feed) operates on whatever the 64 seeded keywords happen to return, and there is currently no way to add one without writing SQL against the `savedsearch` table. Coverage is also the single biggest driver of how many deals exist to be found: `0003` explicitly rejected cutting saved searches as a way to save quota, on the grounds that it "directly cuts the product's coverage, which is the wrong thing to trade away". So this is the last remaining piece that makes the system find *more* rather than making it safer or prettier. The complication is that a saved search is not free and its cost is not obvious. Each one costs exactly one Browse call per ingest run, and at a 2-hour interval that is **12 calls per day, per search, forever**. With checking budgeted at 2,800/day against a 5,000/day allowance, the arithmetic gives a hard ceiling of **183 searches**; there are 64 today. An unguarded "add search" button is therefore a direct route back to the outage this project already had once, where the daily quota was exhausted partway through the day and ingestion died with it, silently, for seven hours.

**Decision:** Add CRUD routes at `/saved-searches`, and make the create path **quota-aware by construction rather than by documentation**. `POST` computes the projected daily call cost including the new search and rejects with `409 Conflict` if it would exceed the allowance, returning the arithmetic in the error body so the answer is actionable rather than a bare refusal. `GET` returns the current searches alongside a budget summary (searches in use, calls per day, remaining capacity), so the cost is visible at the moment someone is deciding whether to add another, not buried in a settings comment. Deletion is offered but **disabling is the default gesture**: `SavedSearch` gains an `enabled` flag and ingestion skips disabled rows, because `last_result_total` and `last_run_at` are accumulated observability that a delete would throw away, and because a search paused to free quota is usually meant to come back. Keywords are normalized and de-duplicated case-insensitively, since two searches differing only in capitalisation return the same eBay results and cost twice.

**Alternatives considered:** Leaving the quota check as a warning rather than a hard refusal was rejected: warnings are read once and the failure mode here is delayed and silent, which is precisely the combination that produced the original outage. Automatically lowering the ingest frequency to make room for more searches was rejected as too clever, since it changes a global behaviour to satisfy a local request, and `0003` already reasoned that ingest frequency is the last thing that should be cut. Automatically disabling the least productive search to make room was considered and rejected for the same class of reason: it makes a destructive judgement on the user's behalf, and "least productive" is not well defined when a search that returns few results may be returning exactly the rare items worth finding. Hard-deleting rather than disabling was rejected because of the observability loss above. Allowing the ceiling to be overridden by a setting was rejected because the ceiling is not a preference, it is arithmetic against a measured allowance; if the interval or budget changes, the ceiling recomputes from them automatically.

**Consequences:** Migration `0015` adds one indexed boolean, defaulting to true so every existing search keeps working. `ingest_all` gains a filter, which is the one place a bug here would be invisible, so a test asserts a disabled search is never queried. The projected-cost calculation reuses `estimate_daily_calls` from `connectors/disappearance_check.py` rather than duplicating the arithmetic, which means the ceiling automatically tracks `ingest_interval_seconds` and `disappearance_check_budget`: halving the ingest interval halves the number of searches that fit, and the API will start refusing at the right point without anyone remembering to update it. The routes are unauthenticated like the rest of the API, which is acceptable only because the stack is local-only and is the subject of the next piece of work; a `POST /saved-searches` reachable from the internet is a way to burn someone's API quota. Finally, this closes the loop between the two halves of `0003`: that ADR protected the quota from the *checker* with a budget and a reserve, and left the *ingest* side protected only by the fact that nobody could easily add searches. This makes that protection explicit instead of accidental.
