# 0017 - An API key on writes, and failing closed when it is not configured

**Context:** Three endpoints now write to the database and none of them checks anything: `POST /capture` inserts listings, and `POST`/`PATCH`/`DELETE /saved-searches` change what the pipeline ingests. That was acceptable while nothing wrote and the stack was a local experiment, and it stopped being acceptable when the saved-search CRUD landed, because a reachable `POST /saved-searches` is a way to spend **someone else's eBay quota**: each accepted search costs 12 Browse calls a day, forever, and the daily allowance is 5,000. An attacker does not need to exfiltrate anything to do damage here; they need to add searches until ingestion starves, which is the same outage `0003` documents and which took seven hours to notice the first time. `POST /capture` is the milder case but still writes unvalidated rows into the corpus that stage 4 prices against. This is also the last thing standing between the project and stage 7, since nothing should be deployed while every write is open.

**Decision:** Require an API key on every mutating request, checked against `settings.api_key` and supplied as an `X-API-Key` header. Reads (`GET /listings`, `/deals`, `/saved-searches`) stay open, because they expose the user's own corpus rather than anything sensitive, a frontend and the extension's match display both need them, and gating them buys little against the threat that actually matters, which is unwanted writes. `/health` stays open so a container probe does not need a secret. **When no key is configured, writes are refused rather than allowed.** That is the whole decision: an unset secret means the system fails closed, with an error that says how to configure it, rather than silently running wide open.

**Alternatives considered:** Treating an empty `API_KEY` as "auth disabled" is the conventional choice and was rejected deliberately. It optimises for the first five minutes of local development and produces exactly one catastrophic outcome: someone deploys, forgets the variable, and every write endpoint is public with no error anywhere to notice. Failing closed inverts that, so the mistake surfaces as a clear 503 at the moment it is made, and the cost is one line in `.env`. Binding to localhost only, and skipping auth entirely, was rejected because it is not a property this code can enforce (a reverse proxy or a container port mapping undoes it) and because it would still be wrong the moment the frontend or extension ran from anywhere else. Full user accounts with sessions and password hashing were rejected as disproportionate: this is a single-user tool with one operator, and the extra surface (registration, resets, session storage) would be more code to get wrong than the thing it protects. JWTs were rejected for the same reason, plus they solve a problem this project does not have, since there is nothing to distribute a claim to. Signing requests was rejected as needlessly complex against a threat model that is "do not let strangers write to my database".

**Consequences:** One setting, one dependency, and a header. The browser extension gains a configurable key that it sends with every capture, which means it now needs a settings surface it did not have; the popup grows one field, stored in `chrome.storage.local` rather than hardcoded so the repo never contains the secret. `.env.example` documents the variable and says plainly that leaving it empty disables writing rather than disabling checking. Comparison uses `secrets.compare_digest`, which is habit rather than necessity at this scale but costs nothing and means the code does not model a timing leak for a future reader to copy. The tests grow a fixture that sets a key, and one that asserts writes are refused when none is set, since fail-closed is the behaviour most likely to be "fixed" by someone who reads it as a bug. Worth stating what this does **not** do: it authenticates the operator, not the data. A stolen key can still add saved searches, and nothing here rate-limits, audits, or scopes what a key may do. Those are real gaps and they are the right ones to defer for a single-user local tool, but they should be revisited before this is ever multi-user, at which point per-key scopes and an audit trail become the interesting design questions rather than an afterthought.
