# 0006 - Capturing what eBay already sends, including the getItem body we already spend quota on and discard

> Throughout this project, "cost", "spend" and "budget" refer to **eBay's daily
> call quota, not money**. The Browse API is free at this tier; what is scarce
> is the 5,000 calls/day measured in `0003-ebay-call-budget.md`.

**Context:** An audit of what the Browse API actually returns, against what the normalizer actually reads, found the connector using a small fraction of each response. Four omissions matter. **`epid`**, eBay's catalog product identifier, is present on `itemSummary` and dropped: two listings sharing an `epid` are definitively the same product, which is exactly what stage 3's CLIP embeddings and NLP brand/model extraction are both built to approximate, and it is free and exact. **`itemEndDate`** is dropped, which is worse than it sounds twice over: `0005`'s expiry heuristic guesses at 30-day terms with a tolerance window when eBay states the real scheduled end outright, and the field is *not returned for Good 'Til Cancelled listings*, so its absence identifies precisely the auto-renewing listings that generate the false sales relist detection exists to catch. **`bidCount`** is dropped, and for auctions it is close to decisive: an auction ending with bids sold, one ending with none did not, which removes the need to infer sale-versus-expiry for that whole class of listing. And **the entire `getItem` response body is discarded**: `check_listings_for_source` calls `getItem` on every candidate and reads only whether it 404s, throwing away `localizedAspects` (structured Brand, Model, Storage Capacity name/value pairs) and `estimatedAvailabilities.estimatedSoldQuantity` (actual units sold, which is real sales data rather than inference). That last one also partly reverses the reasoning in the stage 3b sketch, which rejected fetching structured aspects on the grounds that the call budget forbade an extra request per listing: the request is already being made and its quota already spent, so for any listing the checker touches, the aspects cost nothing extra.

**Decision:** Read the fields already present in responses already fetched, and pay nothing extra for any of it. From `itemSummary`: `epid`, `item_end_date`, `bid_count`, `seller_feedback_score`, `seller_feedback_percent`, and `qualified_programs` (Authenticity Guarantee and similar move price materially in some categories). From the `getItem` body the disappearance check already receives: `localizedAspects` into a JSON `aspects` column, and `estimatedSoldQuantity`. Rewrite `0005`'s `_looks_like_term_expiry` to use the real `item_end_date` when present, keeping the 30-day guess only as the fallback for listings that predate this change, and treat a missing `item_end_date` on a non-auction listing as the GTC marker it is. Use `bid_count` in sale confidence: an auction that disappears having never received a bid did not sell, and should score near zero as a comp, while one that disappears with bids sold and should score high. `epid` is captured and indexed now but nothing consumes it yet; the first thing to do once real data lands is measure its coverage, because that number determines how much work stage 3 actually has to do.

**Alternatives considered:** Polling each auction shortly before its `itemEndDate` to capture a near-final bid was considered and deferred rather than rejected. It would produce the highest-quality comp available anywhere in this system, a price somebody actually paid, and the budget has room. It is deferred because it needs scheduling machinery the scheduler does not have (per-listing timed jobs rather than fixed intervals), and because `bid_count` at disappearance already delivers most of the sold-or-not signal for a fraction of the effort. Revisit once auctions are measured as a meaningful share of the corpus. Capturing `localizedAspects` by adding a dedicated `getItem` call per listing at ingest was rejected on the same call-budget grounds as before; the point here is precisely that no new call is needed. Parsing `localizedAspects` into typed `brand` and `model` columns immediately was rejected as premature: the aspect names vary by category, coverage is unknown, and stage 3b should design that mapping against real data rather than against an assumption.

**Consequences:** The normalizer stops being a thin field-mapper and takes on light interpretation (deriving `is_gtc` from an absent end date, flattening aspects), which is a reasonable place for it but worth noticing. `get_item` now returns a body the caller must handle rather than a bare truthiness check, so `SourceClient` gains a slightly larger contract that `connectors/depop.py` will have to satisfy. Sale confidence gets meaningfully better for auctions and for anything with a real end date, and correspondingly the confidence scores written before this change are not comparable with the ones written after, which matters when reading early data. `aspects` and `qualified_programs` are JSON and unindexed on purpose, since nothing queries them yet and stage 3b should decide what deserves promotion to a typed column. Most importantly, `epid` coverage is now measurable, and if it is high then exact catalog matching is a better comp key than either embeddings or regex extraction, which would make stage 3 substantially less load-bearing than the build order assumes. That is a question for data, not for this ADR, and it is deliberately left open.
