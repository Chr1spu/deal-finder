# 0001 - Multi-source connector strategy: push vs. pull ingestion

**Context:** Stage 1 built one connector, eBay, against its official Browse API: a scheduler polls a saved search, normalizes the results, and periodically re-checks tracked listings to build sold-price history. The next two sources actually planned, Depop and Facebook Marketplace, do not fit that pattern the same way. Depop has no official API, but its own web app calls unofficial JSON endpoints that hobby projects commonly use. Facebook Marketplace has no API at all, its ToS explicitly prohibits scraping, and it is login-walled with active bot detection. Before writing any Depop or Facebook code, the project needs one settled answer for how a listing from a source with no sanctioned API actually gets into the `Listing` table, instead of each connector inventing its own answer. OfferUp is out of scope for this decision and stays deferred until it is actually prioritized.

**Decision:** Split sources into two ingestion shapes based on whether server-side automated access is viable at all.

eBay and Depop stay pull-based: a server-side client (`EbayClient`, and a new `DepopClient` following the same shape) polls on a schedule, normalizes results into `Listing`, and gets checked periodically by `disappearance_check.py` (generalized to loop over every pull-based source instead of being eBay-only) to build sold-price history. Depop is explicitly lower-investment than eBay, same as already documented: expect its unofficial endpoints to break without notice, and do not chase fixes hard when they do.

Facebook Marketplace goes push-based instead: a browser extension, running in the user's own logged-in session, lets the user click "capture" on a listing they are already viewing. The extension reads that one page and posts it to a new capture endpoint on the API, which normalizes it into a `Listing` with `source="facebook"` the same way any other source does. No server ever requests a Facebook Marketplace page on its own. There is no automated disappearance-check for Facebook listings; their freshness depends on the user happening to re-capture them later.

**Alternatives considered:** Scraping Facebook Marketplace server-side, the same way as Depop, was rejected. Facebook's ToS prohibits it outright and its bot detection is strong enough that a hobby-scale scraper is likely to get blocked rather than degrade gracefully, a materially different risk than Depop's unofficial-but-unenforced endpoints. A server-side fetch triggered by a URL the user pastes in was also considered and rejected: it looks safer than a general scraper, but it is still a server making an automated-looking request to a login-walled page it has no session for, so it does not actually avoid the underlying problem. Skipping Facebook Marketplace entirely (eBay and Depop only) was rejected because Facebook is one of the two sources the project wants to cover next.

**Consequences:** Ingestion is no longer one shape. `connectors/` gains a pull-based `depop.py` mirroring `ebay.py`, while Facebook gets a push-based API route instead of a scheduled script, and a new `extension/` directory enters the repo for the browser extension's own source. `disappearance_check.py` needs to loop over sources instead of being hardcoded to eBay. Sold-price history stays reliable for eBay and Depop but is inherently weaker for Facebook, since nothing re-checks a captured listing unless the user does it again by hand, an accepted tradeoff given the alternative is not supporting Facebook at all. `SavedSearch` (keyword plus location, polled on a schedule) does not apply to Facebook listings, which arrive one at a time from whatever the user happened to be browsing, not from a standing query.
