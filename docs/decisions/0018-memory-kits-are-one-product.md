# 0018 - A memory kit is one product, and its capacity is the total

**Context:** `0013` closed with a limit it could not explain: DDR5 desktop memory kept a **19.1x** price spread after capacity, generation and form factor had all been matched, and the note recorded the suspect as "single sticks against multi-stick kits, which needs a quantity-within-listing concept distinct from `lot_size`". Reading the capacity pattern against real title shapes shows the mechanism, and it is worse than the suspicion. `_CAPACITY_RE` requires a word boundary before the number, so the two ways sellers write a kit fail in two different ways: **"2x16GB" yields no capacity at all** (there is no word boundary between `x` and `16`), and **"16GB x 2" yields 16**, the per-module size. The first case is the damaging one. Capacity is a soft filter that keeps unstated rows, by design, because 89% of titles state nothing. So a kit written "2x16GB" was not merely misfiled, it was eligible as a comp for *every* capacity at once: an 8GB stick and a 128GB kit alike. The same physical product written "32GB (2x16GB)" already read 32 and behaved correctly, so identical items sat in different buckets depending only on how the seller typed the title.

**The reason this was not fixed with the obvious pattern is recorded in `_LOT_COUNT_RE`.** Generic "Nx" quantity forms were measured against this corpus and rejected: they matched 1,789 listings, 14.1%, and essentially all falsely, because in PC hardware an x beside a number is a PCIe lane count ("PCIe 4.0 x16"), a product line ("VENTUS 3X PLUS") or a CPU model ("Ryzen 5 7600X"). Any kit rule has to clear that bar.

**Decision:** Add `_KIT_RE`, matching only a quantity that is immediately followed by a capacity unit, in either order: `2x16GB`, `4 x 8GB`, `16GB x 2`. Requiring `GB` or `TB` right after the second number is what makes it safe, because not one of the false-positive forms above is followed by a capacity unit. Module counts outside 2 to 8 are ignored: `1x8GB` is a single stick written oddly, the same call `MIN_LOT_SIZE` already makes, and a larger number in front of an x is a model or a lot rather than a slot count. `_capacity_gb` now takes the largest of the plain capacities and the kit totals, so both spellings of the same kit resolve to the same number. The rule is gated on `_COMPONENT_CONTEXT_RE`, the same memory/storage gate `_form_factor` uses, and here that gate is load-bearing rather than tidy: "RTX 3090 24GB x 2" is two graphics cards, and totalling it to 48GB would file the listing under a capacity no card has, leaving it with **no** comps rather than merely bad ones. The module count is recorded in `variant_signals` as `kit_modules` and `kit_total_gb`. It is not a comp filter and not a column.

**A kit is not a lot, and that distinction is the whole rule.** `lot_size` excludes a listing from comps entirely, because a lot of fifty measures a different quantity than one item. A matched memory kit is the opposite case: it is *one* product, sold and priced as a unit, that a buyer cannot split without changing what it is. So the count feeds capacity, which keeps the listing usable as a comp at the price it actually commands, rather than feeding `lot_size`, which would delete it from price history. That is the "quantity within a listing" concept `0013` asked for, and it turns out not to need a new column to express, only the recognition that for memory the quantity is already denominated in the units capacity is measured in.

**Alternatives considered:** A `module_count` column applied as a soft comp filter was rejected *for now*, not on principle. A single 32GB stick and a 2x16GB kit are genuinely not the same product, so the filter may prove worth it, but every filter added to this pipeline excludes real data and the project's rule is to measure before paying that cost. `ml/measure_kit_rule.py` produces the number that decides it: whether within-bucket spread stays high after kits are totalled. Widening `_CAPACITY_RE` to drop the leading word boundary, which would make "2x16GB" read as 16, was rejected because it is a corpus-wide change to the field every spec filter depends on, and it would produce the *wrong* answer here anyway (16, not 32). Treating a kit as a lot was rejected as described above. Parsing the module count out of eBay's `localizedAspects` was rejected on `0013`'s measurement: aspects carry capacity on 0.3% of graphics cards and 12% of RAM, so the title is the only place this information reliably exists.

**Consequences:** Extraction must be re-run for the change to reach stored rows (`python -m ml.extract_listings`), and per `CLAUDE.md` the workers must be restarted **first**, or the next ingest cycle overwrites the corrected rows with output from the pre-fix code held in worker memory. That has happened three times. The corpus-wide validation this project requires before trusting an extraction change has **not** been run yet, because it needs the real database: `python -m ml.measure_kit_rule` reports the change rate, the affected categories, a sample of changed titles, and DDR5 desktop spread before and after. The expected shape is a change rate in the low single digits; a double-digit rate means the pattern is catching something other than kits and the rule should come back out, exactly as the generic Nx forms did at 14.1%. The rule is written against memory and storage vocabulary, so like every other rule in `ml/extract.py` it needs the cross-category checks re-run when saved searches move into new categories: "2 x 4ft" on a curtain listing is the shape to watch for, currently excluded only because it carries no GB.
