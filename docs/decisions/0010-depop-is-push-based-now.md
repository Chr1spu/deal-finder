# 0010 - Depop moves from pull to push: the unofficial endpoints are gone

> Supersedes the Depop half of `0001-multi-source-connector-strategy.md`. The
> pull-vs-push *axis* in 0001 still stands, and so does everything it says
> about eBay and Facebook Marketplace. What changed is which side of that axis
> Depop belongs on, and the reason is a measured fact about Depop rather than
> a change of preference.

**Context:** `0001` put Depop on the pull side, on the stated premise that "its own web app calls unofficial JSON endpoints that hobby projects commonly use" and that these were unofficial-but-unenforced, a materially lighter situation than Facebook's active bot detection. That premise was true when it was written and is not true now. Measured on 2026-07-25, every Depop host returns **`403 Forbidden` to server-side requests**, including `https://www.depop.com/robots.txt` itself, `https://www.depop.com/search/`, and the `webapi.depop.com` v1 and v2 product-search endpoints the old hobby-project recipes use. The response headers identify the mechanism: `Server: cloudflare` with a `__cf_bm` cookie, which is Cloudflare Bot Management. A control request to `example.com` in the same session returned 200, so this is Depop refusing automated clients, not a broken network. Separately, Depop does have an official API, and it does not help: the Selling API at `partnerapi.depop.com` is partner-gated and scoped to managing *your own* inventory and orders. It is not a marketplace data API, so even if access were granted it would not return other people's listings, which is the only thing this project wants from Depop.

**Decision:** Depop becomes a **push-based source**, captured the same way Facebook Marketplace already is in `0001`: a browser extension running in the user's own logged-in session, which reads the listing page the user is already looking at and posts it to a capture endpoint on this project's API. No server here ever requests a Depop page. `connectors/depop.py` is not written, `DepopClient` does not exist, and `"depop"` is never added to `PULL_BASED_SOURCES`. The capture path is shared rather than Depop-specific, because it is the same problem twice: `POST /capture` accepts a normalized payload with a `source` field, and one extension handles both Depop and Facebook Marketplace with per-site page parsers. A captured listing lands as an ordinary `Listing` row with `source="depop"`, which means it is automatically excluded from disappearance tracking (not in `PULL_BASED_SOURCES`) and from comp building (not in `COMP_SOURCES`), exactly as `0008` requires. It then gets embedded by the existing `embed_pending` job, since that job selects on `embedded_at IS NULL` regardless of source, and becomes queryable against the eBay reference index built in `0009`.

**Alternatives considered:** Defeating the bot protection was rejected, and it is worth being precise about why rather than waving at it. It would require impersonating a browser at the TLS and fingerprint level, and possibly rotating residential proxies. That is detection evasion, it is the thing Cloudflare Bot Management exists to stop, and this project already rejected a *far* milder version of it: `CLAUDE.md` refuses to scrape eBay's sold-listings pages on the strength of a `robots.txt` rule, with no active blocking involved at all. Depop is now the stronger case against, not the weaker one, so scraping it would mean applying a looser standard to the site that is more explicitly refusing. Commercial Depop scraper APIs exist and were rejected for the same reason with an extra one: they do the evasion on your behalf, which relocates the problem without changing it, and they add a paid external dependency to a source `CLAUDE.md` explicitly says not to invest heavily in. Waiting for the endpoints to come back was rejected as a plan, since Cloudflare deployment is a deliberate act that is unlikely to be reversed. Dropping Depop entirely was rejected because the capture route costs little on top of the extension `0001` already committed to building for Facebook, and because Depop remains a genuinely good fit for the product: it is the kind of place underpriced items get listed by people who do not check comps.

**Consequences:** The `extension/` directory `0001` anticipated now arrives earlier and matters more, since it is the *only* route to two of the three sources rather than just to Facebook. Coverage on Depop drops from "poll 64 saved searches on a schedule" to "whatever the user actually browses", which is a real and unavoidable loss: there is no automated discovery of Depop deals any more, only valuation of listings the user brings. That reframes the product slightly and honestly, from "it finds deals for you everywhere" to "it finds deals on eBay automatically, and tells you instantly whether anything you are looking at elsewhere is underpriced". `SavedSearch` remains eBay-only, as does the scheduler's ingest job. Captured listings have no reliable disappearance signal, so they can never become comps even in principle, which is a constraint `0008` already imposed for different reasons and which is now doubly true. The capture endpoint is unauthenticated for now because the whole stack is local-only, and that has to change before anything is deployed, which is stage 5's auth work; it is recorded here so it is not forgotten. Finally, this is the second time a source's access assumption has expired between being written down and being built (`0003` found eBay's bulk and Insights APIs 403 the same way), which is a decent argument for verifying access *before* an ADR commits to a mechanism, not after.
