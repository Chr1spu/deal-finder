# 0003 - Living inside eBay's 5,000-call day: search as a liveness oracle, and never deleting listings

**Context:** The pipeline was silently down for roughly seven hours before anyone noticed. Every scheduled job failed with `429 Too Many Requests`, and the eBay Developer Analytics `getRateLimits` endpoint explains why: this application gets **5,000 Browse calls per day**, shared across `search_items` and `get_item`, and `remaining` was **0**. The disappearance check as built (stage 2) issues one `get_item` per active listing, so at 10,496 active listings on a 6 hour interval it wants about 42,000 calls per day. It exhausts the entire daily budget partway through its first pass, and everything after that fails, including ingestion. Three things made it worse: `ingest_all` had no per-search error isolation, so one 429 on the first saved search killed all 64; `call_with_backoff` retried the 429 five times, and a daily-quota 429 never recovers in seconds, so each call burned five times the quota it needed; and nothing was watching, so the failure was invisible. Two eBay APIs that would solve this outright were checked and are not available to this application: the bulk `getItems` endpoint (up to 20 ids per call, a 20x reduction) returns `403 errorId 1100`, and eBay refuses to mint a token for the `buy.item.bulk` scope at all (`invalid_scope, exceeds the scope granted to the client`). The Marketplace Insights API, which returns real sold prices for the last 90 days and would largely replace disappearance tracking entirely, fails the same way. Both are Limited Release APIs requiring a separate application to eBay.

**Decision:** Stop treating the check as a sweep over everything active, and make it spend quota only where there is genuine doubt. Ingestion already refreshes `last_seen_at` for every listing that appears in any of the 64 saved searches, at zero extra cost, and eBay only returns active listings from search, so a listing seen in the latest ingest is provably alive and must never be spent a `get_item` on. This is a one-sided oracle, which is exactly what is needed: presence proves alive, absence proves nothing (a live listing can simply fall below the 200-result cap), so it justifies skipping checks without ever justifying a false "sold". Confirmation stays a real API call, so nothing is marked `likely_sold` on the strength of a search miss. Candidates are then ordered oldest-`last_seen_at` first, since those are the likeliest to actually be gone, and capped by a per-pass budget derived from the **real** remaining quota via `getRateLimits` (which is metered separately and therefore cheap to ask), minus a reserve that protects the next few ingest cycles. Quota exhaustion (`errorId 2001`) becomes a `QuotaExhaustedError` that aborts the run cleanly and returns partial counts, rather than a retryable status: this is the circuit breaker `PROJECT_PLAN.md`'s systems layer always called for and never got. `ingest_all` gains per-search isolation so one failure costs one search instead of 64. Listings that never sell and never end (eBay fixed-price listings can auto-renew indefinitely) are retired to a new `stale` status once they have been active a long time and unseen in search a long time, which is the only thing that actually bounds the active set; they stay in the database and ingestion reactivates them for free if they reappear. And, stated explicitly because the instinct to do otherwise is natural and wrong: **listings are never deleted.** `likely_sold` rows are the product, they are the comp data stage 4 consumes, and the entire reason disappearance tracking exists is that no sold-price API is available here. They also cost nothing in the loop that matters, since the check only ever queries `status = 'active'`.

**Alternatives considered:** Bulk `getItems` was the original plan and is strictly better, turning a 10,496-listing sweep into about 525 calls against what is even a separate 5,000/day meter, but it is not available to this application and was verified 403 before any code was written around it. Marketplace Insights is better still in principle, since real sold prices would remove the need to infer sales from disappearance at all, and it is also 403; in practice it appears to be granted only to established partners, so the realistic planning assumption is that it never arrives. Neither scope is a dependency of this decision: the design below assumes 5,000 shared calls a day and nothing else, and would simply have more headroom if `buy.item.bulk` were ever granted. Reducing the number of saved searches would cut call volume proportionally but directly cuts the product's coverage, which is the wrong thing to trade away. Lowering the ingest frequency was rejected as the primary lever for the same reason: ingest is both the product (finding a deal early is most of the value) and the cheapest liveness data available at 200 listings per call, so it is the last thing that should be cut. Deleting or archiving sold listings to keep the table small was rejected outright: it targets disk, which is not the constraint (about 3.4 KB per row once embeddings land, so a million listings is roughly 3.4 GB), and it would destroy exactly the data the valuation engine is being built to consume.

**Consequences:** Sold-detection latency for a listing that has fallen out of search coverage is now measured in days rather than hours, and that is an accepted cost of the 403, not a design preference. The check's call cost scales with churn rather than corpus size, which is what makes it safe to leave running as the corpus grows. `ListingStatus` gains `stale`, so any code branching on status must handle three values instead of two, and `PULL_BASED_SOURCES` clients now need a way to report quota. New settings (`disappearance_check_budget`, `quota_reserve`, `stale_after_days`, `unseen_after_days`) are all tunable, deliberately, because their right values are unknown: the corpus is one day old and `ingest_saved_search` currently returns a single `upserted` count that does not separate inserts from updates, so the arrival rate that drives all of this has never been measured. That counter is split in this change so the numbers can be checked against reality in a week. The retirement thresholds are the weakest part of this decision and should start conservative, since a wrongly retired listing stops being a sold-detection candidate while retired, which silently costs comp data. Finally, a related limitation is now on the record for stage 4: a listing disappearing means sold, **or** expired unsold, **or** withdrawn by the seller, and Browse cannot distinguish them, so `likely_sold` must be read as "left the market at this asking price" and never as "sold at this price". The valuation engine's confidence weighting has to account for that, and a listing that vanishes very early in its listing duration is weaker evidence than one that vanishes late.
