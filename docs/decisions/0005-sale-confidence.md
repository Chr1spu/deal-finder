# 0005 - Sale confidence: relist detection, listing duration, and never calling a disappearance a sale

**Context:** The valuation engine's whole premise is that a `likely_sold` listing is a comparable sale, and it isn't one. A listing leaves the market when it sells, but also when it expires unsold, when the seller withdraws it, and (very commonly on eBay) when a Best Offer is accepted well below the asking price that gets recorded. Every one of those failure modes biases the recorded comp *upward*, which means the median comp sits above true market, which means every listing scores as a better deal than it is. A systematic bias toward false positives is the worst possible direction for a deal finder. `0003` recorded the ambiguity as a known limitation and deliberately left it unsolved; `0004` added `accepts_best_offer` and `missing_since` without yet using them. The obvious external fix, reading the sold prices eBay publishes in its own web UI, was investigated and rejected: eBay's `robots.txt` disallows `/sch/` with three separate rules covering the sold-search path specifically, and states that automated access without express permission is prohibited, pointing to the official API instead. Marketplace Insights, which would answer this properly, is documented as not grantable on request. So the accuracy has to come from data already held, and the important realization is that quite a lot is available there and none of it is being used.

**Decision:** Stop treating disappearance as a binary sold/not-sold and attach an explicit confidence to every inferred sale, computed from three signals already in the database. First, **relist detection**: when a listing disappears, check whether another listing from the same source carries the same `image_hash`, either already active or appearing within a grace window afterward. eBay fixed-price listings auto-renew under new item ids constantly, so a matching photo elsewhere is strong evidence the item did not sell but was relisted, and that comp is false. This reuses the `image_hash` column `0002` built and left unused, applied to same-source relists rather than the cross-source matching that ADR deferred, and it costs zero API calls because it is a pure database question. Second, **listing duration**: `missing_since - posted_at` separates a listing that vanished in three days (likely sold) from one that vanished at roughly the length of a standard listing term (likely expired). Third, **Best Offer**: a listing with `accepts_best_offer` sold at an unknown discount to the recorded asking price, so its price is weaker evidence than a fixed-price listing's. These combine into a stored `sale_confidence` float and a `sale_signals` JSON breakdown on `Listing`, written when a sale is confirmed. Stage 4 must weight comps by that confidence rather than counting them equally, and must exclude confirmed relists outright.

**Alternatives considered:** Scraping eBay's sold-listings search was the direct solution and is rejected above on the strength of an explicit machine-readable directive covering exactly that path, which is a materially clearer prohibition than the undocumented endpoints `0001` accepted for Depop, and which puts the eBay account and the developer keyset (the same identity) at risk. A user-driven browser extension capturing sold pages the user is already viewing remains open and is the sanctioned route to real sale prices; it is complementary to this decision rather than an alternative, since it is manual and low-volume and this needs to work automatically across the whole corpus. Storing a plain boolean `probably_relisted` instead of a confidence score was rejected because the three signals disagree in interesting ways and collapsing them early throws away the information stage 4 needs to weight a comp. Computing confidence at query time in stage 4, rather than storing it, was rejected because relist detection depends on what the database looked like around the disappearance, and a query run months later would see a different world.

**Consequences:** Comps stop being equal-weight, so stage 4's scoring gains a required input it must not ignore, and "how many comps" becomes a weaker summary than "how much total confidence." Relist detection is only as good as `image_hash`, so it misses relists where the seller changed the photo and produces false matches for stock photography, which is common for boxed retail goods and is precisely where it will be least reliable; the `sale_signals` breakdown keeps that visible per listing rather than burying it in one number. The grace window for a relist appearing is a guess and is a setting. Most importantly this makes the problem **measurable** for the first time: the share of disappearances that are relists, and the distribution of listing lifetimes, are both currently unknown, and the first honest read of the deal scanner's real accuracy depends on them. If relists turn out to be a large fraction, that is an argument for revisiting the browser-extension route with real numbers behind it rather than as a hunch.
