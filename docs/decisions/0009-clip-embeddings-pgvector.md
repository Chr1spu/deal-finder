# 0009 - CLIP embeddings in pgvector: the eBay corpus as a reference index

**Context:** Stage 3 is the feature pipeline, and ADR 0008 changed what it is for. The original build order justified embeddings as a general similarity feature, one input among several to a multi-source comp engine. Under 0008 there is no multi-source comp engine: eBay is the sole price oracle, and Depop and Facebook Marketplace are valuation clients whose listings get scored *against* eBay value. That turns the hard problem into cross-source item identification, and it changes what embeddings are: **the eBay corpus becomes a reference index that foreign listings are queried against.** The alternative identity key, `epid` (ADR 0006), is exact and free but is an eBay *catalog* id, so a Depop or Facebook listing does not carry one and never will. `epid` is therefore excellent for eBay-internal comps and structurally useless for the bridge, which settles a question that had been left open: `CLAUDE.md` gated stage 3 on measuring `epid` coverage, on the theory that high coverage might make embeddings redundant. It cannot, whatever the number turns out to be. The measurement still matters for how stage 4 keys eBay-internal comps; it is not a gate on this work. A related asymmetry falls out of the same reframing and shapes the design: eBay embeddings are the index and foreign embeddings are queries, so a missing eBay embedding removes a possible match for every future query, while a missing Facebook embedding costs exactly one lookup.

**Decision:** Embed listing images with `open_clip_torch` running `hf-hub:laion/CLIP-ViT-B-32-laion2B-s34B-b79K` (512 dimensions, fp32) and store the vectors in a nullable `vector(512)` column on `listing`, via pgvector. `create_model_and_transforms()` returns the model together with its own preprocessing transform, so normalization constants cannot silently drift apart from the checkpoint, and swapping to SigLIP later is one string. Vectors are L2-normalized at write time and queried with cosine distance (`<=>`) at read time: cosine is self-defending if a row ever lands unnormalized, where inner product would silently rank by magnitude, and `1 - (a <=> b)` falls in `[0,1]`, which is what stage 4's match-confidence score needs. Images are fetched at eBay's `s-l500` CDN variant rather than the `s-l225` stored at ingest, by URL substitution, which costs no API quota because the CDN is not the Browse API. Embedding runs as its own job on its own `deal-finder-ml` RQ queue, never inline in ingestion. Backfill and go-forward are deliberately the same code path: `embed_pending()` selects `WHERE embedded_at IS NULL`, which is simultaneously the existing corpus and every row ingestion lands from now on. `embedded_at` is stamped on every attempt, success or failure, so imageless listings and dead image URLs are not retried forever. No ANN index is created yet.

**Alternatives considered:** Embedding inline in `ingest_saved_search`, the way `image_hash` is computed (ADR 0002), was rejected, and the contrast with that ADR is the point: hashing is cheap CPU work with no heavy dependency, embedding is neither. Inline would put torch in the ingest worker's process (forcing a single fat GPU image in stage 7), let a CUDA fault take down *data ingestion* rather than just a feature job, add GPU work to a run that is already ~30 minutes and sequential, and force batch size 1. A shared RQ queue was rejected for a reason that is about capability rather than throughput: RQ hands a worker whatever job is next, so the torch-free ingest worker would eventually be handed an embed job and die on `import torch`. Storing vectors as JSON and computing distances in Python was rejected as it forfeits the indexable-later property that is the entire reason to use Postgres for this. Building an HNSW index now was rejected as premature: an exact scan measured 29 ms in Postgres over the full 10,484-vector corpus (~68 ms end to end once ten `Listing` objects are hydrated), at 100% recall, and stage 4's queries are *filtered* k-NN (by source, sale confidence, category), which ANN indexes handle poorly; revisit near 100k rows or a measured query above ~100 ms. (This paragraph originally asserted single-digit milliseconds, which was an estimate rather than a measurement and was wrong by roughly an order of magnitude. The conclusion survives the correction, but it is worth recording that it was checked rather than assumed.) A larger checkpoint (ViT-L, SigLIP) was rejected for now because the expected failure mode is not resolution but category-level retrieval, and a bigger vision model does not fix that; see Consequences. Making the model name a setting was rejected because it must agree with the dimension the migration created, and a `.env` key that can silently disagree with the schema is a footgun; it is a module constant, the same reasoning as `NON_NEW_CONDITION_IDS` in `connectors/ebay.py`. A `TypeDecorator` shim so SQLite could stand in for the column type was considered and proved unnecessary: `pgvector.sqlalchemy.Vector` subclasses `UserDefinedType`, whose DDL goes through the generic type compiler, and SQLite accepts arbitrary type names, so `create_all`, insert, NULL and round-trip all work as-is. That was verified with a two-minute spike before any workaround was written, which is why none exists.

**Consequences:** `pgvector` joins the main dependencies rather than an optional group, because `api/models.py` imports `Vector` to declare the column and everything imports `api.models`; it is small and pure Python, so this costs little. torch, torchvision and `open_clip_torch` go in a PEP 735 `ml` group (extras are unavailable here because `[tool.uv] package = false`), pinned to an explicit PyTorch CUDA index, and the failure mode to watch is silent: without `explicit = true` plus `[tool.uv.sources]`, Windows resolves the CPU-only wheel, everything imports fine, and `torch.cuda.is_available()` is quietly `False`. The venv grows to roughly 3 GB, which is why it moved out of the OneDrive-synced folder first. Alembic cannot autogenerate any of this (it never emits `CREATE EXTENSION` and does not know the `vector` type), so migration `0010` is hand-written and a later `--autogenerate` may propose dropping the column; the `EMBEDDING_DIM` in that migration is hardcoded rather than imported, because a migration describes the schema at its revision and importing a live constant would let a later checkpoint swap silently rewrite history. Adding 512 floats per row also makes an existing problem urgent rather than latent: `GET /listings` has no pagination and already serializes every column of all 10,496 rows, so it gains a `ListingRead` schema with `limit`/`offset` that excludes the vector. Testing splits in two: logic tests keep using the SQLite fixture, while pgvector *behaviour* (the distance operators, the real column type) needs a Postgres fixture that skips rather than fails when the container is not running, so `uv run pytest` stays one green command. Most importantly, the honest limitation: **CLIP retrieves visual similarity, not product identity.** Neighbours will be "three-fan graphics cards" rather than "this exact RTX 3090 SKU", and the price range across a neighbour set will be wide. That is expected, and the fix is a filter over visual similarity (extracted brand/model in stage 3b, or `epid` for eBay-internal comps), not a bigger vision model. The domain shift between clean CDN product shots and a real-world phone photo is the genuine technical risk of this stage, and it is why verification queries the index with a non-eBay photo rather than settling for an eBay-to-eBay demo.

**Measured on the real corpus after this landed, and it sharpens the above into a rule.** Retrieval quality is strongly category-dependent: Nintendo Switch consoles returned neighbours spanning $136 to $242 (directly usable), iPhones $299 to $785 (usable once the model is extracted), and prebuilt gaming PCs $578 to $3,000 (useless). The predictor is whether the price-determining attribute is visible at all: a console *is* the product, while a PC case says nothing about the GPU inside it, and the GPU is most of the price. The consequence for stage 4 is counter-intuitive and belongs on the record: **the similarity score must not be used as a comp confidence weight.** The useless PC neighbours scored *higher* (~0.87) than the useful iPhone ones (~0.77), because interchangeable-looking items score best precisely when their photos carry least information. Similarity is a candidate-generation score only; comp membership has to be decided by extracted attributes or `epid`. This also tells stage 3b where it is worth the most, which is exactly the categories where the image carries least.
