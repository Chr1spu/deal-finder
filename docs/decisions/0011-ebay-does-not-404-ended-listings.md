# 0011 - eBay does not 404 ended listings, so nothing was ever marked sold

> **This corrects the central assumption of `0003`, `0004` and `0005`.** Those
> ADRs designed budgeting, two-strike confirmation and sale-confidence scoring
> on top of a sold-detection signal that could never fire. The machinery they
> describe is sound and is retained unchanged; what was wrong is the one line
> underneath it that decided whether a listing had gone.

**Context:** Disappearance tracking is how this project builds sold-price history, because no sold-price API is available to it (`0003`). The mechanism was: re-check an active listing with `getItem`, and if the call returns 404, the listing has left the market. `EbayClient.get_item` returns `None` on 404 and the check treated `found is None` as the sole signal. **eBay does not 404 ended listings.** Measured against production on 2026-07-25, taking eight listings that had dropped out of search coverage: **zero returned 404.** Four were plainly gone, showing `estimatedAvailabilityStatus: "OUT_OF_STOCK"` and/or an `itemEndDate` in the past, and all four returned HTTP 200 with a full body. The other four were genuinely still live. So the sold branch was unreachable, and had been since stage 2. The database bore this out exactly: 12,420 listings, every one `active`, zero `likely_sold`, zero `sale_confidence` scores, after weeks of the pipeline being nominally live. That was read as "the pipeline keeps dying before it accumulates anything", and the real cause was that a working pipeline would have produced the same zero. A second, smaller error surfaced in the same investigation: `is_gtc` was derived at ingest from a missing `itemEndDate`, on `0006`'s reasoning that eBay omits that field for Good 'Til Cancelled listings. True of a `getItem` body, false of a search response, which **never** contains `itemEndDate` for any listing. Every non-auction row was therefore marked GTC, producing a measured 98.9% that described the endpoint rather than the market. Both mistakes share a shape: a property of one eBay endpoint was assumed to hold for another.

**Decision:** Determine "has this listing ended" from the response body, not the status code, via a new `normalizer.listing_has_ended`. Two independent sufficient signals: `estimatedAvailabilityStatus == "OUT_OF_STOCK"` or `estimatedAvailableQuantity == 0` (for the secondhand single-quantity listings this project tracks, out of stock means sold), and an `itemEndDate` at or before now (unambiguous). A 404 is retained as a third signal, since some listings do eventually disappear entirely. The function is deliberately conservative: an absent, unparseable or unrecognised field means "not known to have ended", so uncertainty leaves a listing active. A false negative costs one re-check on the next pass; a false positive writes a fabricated comp into the dataset permanently. The two-strike confirmation from `0004` is kept on top of this and now matters more, not less, since `OUT_OF_STOCK` can be transient for a multi-quantity seller in a way a 404 never was. Enrichment from the item body moves ahead of the branch and runs unconditionally, because an *ending* listing's body is the most valuable one available (it carries the real `itemEndDate` and `estimatedSoldQuantity`) and was previously discarded for exactly those listings. Separately, `is_gtc` becomes `bool | None`: ingest never sets it, `enrich_from_item_body` settles it in both directions from a real body, and migration `0011` nulls every existing value because they were produced by the broken inference and a wrong value is worse than a missing one.

**Alternatives considered:** Treating a listing's absence from search as the sold signal was rejected, and this is worth restating because it is the tempting shortcut. `0003` established that search presence is a **one-sided** oracle: presence proves alive, absence proves nothing, since a live listing can simply fall below the 200-result cap. Using absence as evidence of a sale would manufacture comps from ranking changes. Treating `OUT_OF_STOCK` as immediately conclusive, skipping the second strike, was rejected on the multi-quantity false-positive risk above; the confirming call is cheap because sales are a small fraction of checks. Trusting `itemEndDate` alone and dropping the availability signal was rejected because Good 'Til Cancelled listings have no end date at all, and those are 80%-plus of this corpus, so it would miss the majority of sales. Keeping `is_gtc` as a non-nullable bool and simply not setting it at ingest was rejected because `False` would then mean both "has an end date" and "never checked", and `sale_confidence` branches on it.

**Consequences:** The immediate one is that it works. The first two check passes after this change marked **241 listings `likely_sold`**, of which **43 were caught as relists rather than sales** by `0005`'s `image_hash` detection, against a lifetime total of zero before it. Sale confidence spans 0.045 to 0.900 with the low end being the relists, which is the scoring in `0005`/`0007` doing exactly what it was built for, on real data, for the first time. Stage 4 now has comps to be designed against rather than an empty table. Detection also gets *faster* than the 404 design would have been, since `OUT_OF_STOCK` appears while eBay is still serving the page. The `is_gtc` correction resets a column across the whole corpus, so any analysis using it before 2026-07-25 is invalid, and the honest current answer for most rows is "unknown" until the check works through them. Two process lessons are worth recording. First, the fixture was complicit: `tests/fixtures/ebay_item_summary.json` was hand-built rather than recorded, and included an `itemEndDate` that real search responses never carry, so every test agreed with the broken inference. The fixture has had the field removed, and the lesson is that a hand-built fixture encodes the author's assumptions and will confirm them. Second, and more uncomfortable: a mechanism can be elaborated across four ADRs, 180 tests and several weeks while its foundational assumption is never checked against one real response. The check that found this took a single API call. Verifying the *signal* before building the machinery on top of it is cheap, and nothing in the previous design forced it.
